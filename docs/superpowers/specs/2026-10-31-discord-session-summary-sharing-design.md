# 작업 세션 요약을 AI별 봇으로 공유하는 첫 시험

상태: **사용자 승인 완료, 오프라인 구현·검증**. 사용자는 2026-10-31 06:53:54 UTC에 이 설계에 따른 구현·오프라인 시험 진행을 승인했다. 계획에 따른 제품 구현과 합성 시험을 수행했다. 봇 변경·token 작업·실전 게시는 수행하지 않았다. 이번 신규 작업은 commit/push하지 않는다.

실행 계획: [Discord 세션 요약 공유](../plans/2026-10-31-discord-session-summary-sharing.md).

추가 기술 검토 반영: 작성 시각·출처까지 포함한 최종 본문을 사람이 확인하고 해시로 고정한다. 알려진 token/개인 경로/Discord mention 형식이 발견되면 치환·절단·분할하지 않고 게시를 중단한다. `allowed_mentions` 억제도 유지한다. 봇+채널+최종 본문 해시 중복키와 별개로 trial/provider당 1회 quota를 영속 보존하여 새 timestamp/summary ID로 불확실 전송을 우회하지 못하게 한다. 봇별 credential과 실행 기록은 분리하고 두 게시를 순차 처리한다. 일반 비밀 탐지의 완전성은 보장하지 않으며 사람 검토가 함께 필요하다. 기존 승인 상한인 최종1,800자/UTF-8 4096bytes를 유지한다.

## 목적과 선택한 방식

기존 demo는 새 무기억 Claude worker가 Discord 질문에 답하는 방식이었다. 이번 목적은 **선택한 실제 작업 세션이 직접 쓴 요약을 해당 AI의 봇으로 공유**하는 것이다. 전체 기록을 가져와 새 worker에게 요약시키지 않는다.

| 방식 | 판단과 tradeoff |
| --- | --- |
| ① 세션이 요약 작성 → 사용자 확인 → 봇의 출력 전용 게시 | 사용자가 선택한 방식. 원래 작업 문맥을 반영하되 전달할 내용과 실행을 제한한다. 게시 자체에는 모델/Gateway가 필요 없다. 출처 확인과 사용자 중계 단계가 필요하다. |
| ② 기존 세션을 외부에서 resume → 자동 요약·게시 | 선택하지 않았다. 문맥 유지에는 편하지만 기존 문맥을 사용하는 추가 turn, 기존 세션의 도구 권한·동시 실행·결과 회수·자동 반복 문제가 생긴다. 현재 안전한 연결은 미검증이다. |

원래 세션에 새 요약을 요청하면 해당 세션의 문맥 비용은 발생할 수 있다. 게시 프로그램은 요약 본문만 보내며 모델을 호출하지 않는다. 전체 token 수나 절감률은 아직 비교측정하지 않았다.

## 출처와 고정 binding

| source-session 참조 | provider | 실제 게시 identity | 출처 표시 |
| --- | --- | --- | --- |
| 기존 지정 대화 ‘코덱스와 Discord 대화 테스트’ | `claude` | `준영-claude` → 승인된 기존 aibot의 실제 bot ID | `user_forwarded`: 사용자가 이 대화에서 받은 요약을 전달. 직접 접근/서명된 세션 검증으로 주장하지 않는다. |
| 현재 Discord 연동을 구현한 Codex 작업 대화 | `codex` | `준영-codex` → 새로 승인·확인할 별도 bot ID | `current_task_authored`: 현재 작업 대화가 자기 작업만 요약. 별도 Windows CLI 세션을 resume했다고 주장하지 않는다. |

각 binding은 source-session 참조 → provider → 실제 bot/application ID → 동일한 고정 `ai_chat` channel/guild → 허용 owner로 로컬에 고정한다. 실제 ID와 개인 PC 경로는 공개 설계에 적지 않는다. Git 제외 로컬 설정에서 확인하고, 본문·`--as`·봇 표시 이름만으로 출처나 권한을 결정하지 않는다. 두 source가 같은 bot ID를 쓰거나 대상/출처를 바꾸면 거절한다. 누락된 두 번째 bot ID를 추측하지 않는다.

Claude에 대한 `claude://` 접근 차단을 우회하거나 연락하지 않는다. 사용자가 요청문을 전달하고 답변을 가져온다. 이 수동 provenance 한계는 메시지와 로컬 영수증에 명시한다. Codex 출처는 확인된 현재 작업 대화의 논리 참조이며 다른 로컬 작업 세션으로 확장하지 않는다.

## 요약과 사용자 확인

- 각 요약은 **완료 / 직접 검증 / 미검증·막힘 / 다음 할 일** 네 항목, 최종 게시문 기준1,800자 및 UTF-8 4096bytes 이내로 제한한다. 넘으면 자동 절단하지 않고 수정 요청한다.
- 비밀·token·인증정보·개인 경로·다른 프로젝트 정보·전체 대화·민감 로그·첨부파일은 제외한다. 멘션을 막고 코드/외부 작업 지시로 해석하지 않는다.
- 사용자에게 두 최종 본문, 출처 표시, 봇 이름, 고정 대상과 건수를 먼저 보여준다. 확인된 본문과 binding의 checkpoint가 바뀌면 새 확인 없이는 게시하지 않는다.
- Claude의 과거98개 재현은 사용자 전달 결과다. Codex의 직접 실행한 전체309개 시험·CI와, 별도 실제 Claude 왕복1건을 서로 바꿔 말하지 않는다.
- source가 요약을 제출해도 자동 게시하지 않는다. 두 요약이 준비되고 사용자가 출발을 확인한 뒤 부모의 별도 시작 신호를 기다린다.

## 출력 전용 게시와 종료

한 번의 batch에 source별 승인된 요약1개, **총2건**만 허용한다. 두 본문 준비 전에는 시계를 시작하지 않는다. 명시 시작 후 최대3분, 두 게시가 확인되면 즉시 종료한다. Gateway·채널 기록 조회·Discord 입력 구독·자동 AI 호출·봇끼리 상호응답·기존 세션 깨우기·자동 재시작은 없다.

따라서 첫 시험에는 slash command 등록이나 실시간 상주/online 표시가 필요하지 않다. 프로그램 전용 token 사용은 모델·입력·로그에 token을 전달하지 않는 경계이며, 현재 동일 사용자 OS에서 모든 파일 접근을 격리했다고 주장하지 않는다.

1. 사용자 확인한 batch/source/summary revision ID와 본문·binding checkpoint를 영속 저장한다. secret 값은 기록하거나 hash하지 않는다. 요약 ID는 재시작 때 새로 만들지 않는다.
2. 전송 전에 one-shot claim을 영속화한다. 각 bot의 프로그램 전용 credential로 실제 bot identity를 검증한 뒤 정해진 AI 채널에만 REST 게시한다. token은 모델/본문/argv/env 상속/로그/문서로 노출·복사하지 않는다.
3. 영수증의 message ID·channel·nonce를 확인해야 게시 완료다. 동일 summary ID 재실행은 이미 게시/보류 상태를 반환하고 다시 보내지 않는다. 같은 ID에 다른 내용·대상은 거절한다.
4. 이번 첫 시험은 자동 재시도하지 않는다. 확실 실패나 불확실 전송이 하나라도 생기면 남은 batch를 멈추고, `not_sent`와 `uncertain/held`를 구분한다. 진행 중 취소도 실제 전송 여부가 불명확하면 held다. 재시작은 claim을 보류하며 이력을 삭제하지 않는다.
5. 두 번째 게시 또는 시간 만료/실패 시 연결과 자신이 만든 자원을 정리하고 accepted/held/not-sent 건수를 보고한다. 부분 성공은2건 성공으로 표시하지 않는다. 운영 daemon은 남기지 않는다.

각 bot의 effective 권한은 AI 채널만 보기/보내기, 사람 채널과 다른 채널은 차단해야 한다. 설치 permissions0만으로 격리를 주장하지 않는다. 첫 시험에는 요약 게시 외 동작을 추가하지 않는다.

## 기존 코드와의 경계

재사용 후보는 `tools/discord-adapter/rest.mjs`의 고정 대상·제한 fetch, `publisher.mjs`의 크기/멘션/nonce/영수증/uncertain 정책, `lib/storage.mjs`의 원자적 저장·writer lock, 우편의 명시 message ID 패턴이다. 필요하면 사용자가 선택한 **우편1건**의 본문을 출처 표시와 함께 가져올 수 있지만 전체 inbox나 세션 로그를 읽지 않는다.

현재 publisher/runtime은 Discord 질문→worker 결과 상태용이다. 요약을 가짜 Discord interaction/질문 답변으로 만들지 않고 별도 summary outbox와 출처/claim 계약이 필요하다. 기존 private pipe·일반 우편 receiver를 바꾸거나 Discord를 Claude/Codex peer로 위장하지 않는다. Codex의 도구0 미입증 입력 실행은 계속 제외한다. 현재 Codex가 자기 요약을 제출하는 출력과, 봇이 Codex를 실행시키는 입력은 별개다.

## 준비와 구체적 승인 단계

1. **이번 단계:** 설계 확인, 사용자 중계용 Claude 요청문과 Codex 요약 초안. 아직 구현·게시하지 않는다. 확인 후 `writing-plans`로 구현/모의 시험 계획을 만든다.
2. **identity 준비:** 기존 aibot을 `준영-claude`로 재사용할 실제 표시 이름 변경, 새 `준영-codex` 앱/봇 생성·설치, 정확한 server/channel 권한 변경은 변경 내역을 보여준 뒤 각각 구체 승인을 받는다. 현재 이름 변경·두 번째 봇 생성은 미실행이다.
3. **credential 준비:** 신규 token 발급/리셋은 사용자가 담당한다. 저장 위치 준비와 실제 프로그램의 인증 사용·지속 접근은 정확한 파일/프로그램/서비스 범위를 구분해 승인한다. 비밀값을 채팅에 요청하지 않는다. 새 영구 session 등록은 첫 시험에 필요 없다.
4. **게시 준비:** 두 실제 bot ID와 effective 권한, 출처 binding, 두 최종 본문, 영속 claim/중복/취소/종료 경계를 모의 검증하고 사용자 확인을 받는다. 그 뒤에만 한 번의3분/총2게시 실행 승인을 요청한다. 새 모델이나 세션을 자동 실행하지 않는다.

성공 판정은 각 source에 대해 사용자 확인한 요약과 실제 bot identity, 고정 AI 채널의 게시 영수증이 일치하고 총2건 후 종료되는 것이다. 먼저 검증된 Claude 단발 왕복1건이나 과거 mock 성공을 이 시험의 성공으로 세지 않는다.

## 현재 Codex 작업 세션의 공유 초안 — 아직 게시하지 않음

- **완료:** Discord mock·사전 점검·Gateway/ACK·제한 Claude worker·게시 경계·이력 보존 prepare/resume를 구현했다. `준영-claude`/`준영-codex` 이름을 설계에 반영하고 `5955864`를 기능 브랜치에 push했다.
- **직접 검증:** 로컬 전체309개 시험과 check/pack dry-run 통과, 같은 commit의 Windows·Ubuntu CI 성공. 별도 실환경 시험에서 Discord→Claude→Discord1건의 ACK·결과·게시와 자동 종료를 확인했다.
- **미검증·막힘:** 기존 Claude 대화 직접 연결, 두 봇의 실제 설정과 작업 요약 게시 시험은 미실행이다. Codex 전체 도구0 입력 실행은 미입증이므로 연결하지 않았다.
- **다음:** 사용자가 전달할 Claude 요약과 이 초안을 확인한 뒤, 승인된 두 identity의 출력 전용 게시를 모의 검증하고 총2건 시험을 준비한다. token·전체 대화·개인 경로는 공유하지 않는다.

## 사용자가 Claude에게 전달할 요청문 — 직접 송신하지 않음

이 대화에서 직접 수행한 Discord·우편 도우미 관련 작업만, 나중에 `준영-claude`로 공유할 요약 초안으로 써줘. 항목은 **완료 / 직접 검증 / 미검증·막힘 / 다음 할 일**, 전체1,800자 이내야. 네가 직접 실행한 결과와 사용자·Codex에게 전달받은 결과를 구분하고, 현재 대화에 근거가 없으면 모른다고 적어줘. 전체 대화·비밀·인증정보·개인 경로·다른 프로젝트 내용은 제외해줘. 파일이나 과거 대화 로그를 새로 읽거나, 시험·코드/설정 변경·추가 worker/봇 실행·외부 전송은 하지 말고 텍스트 초안만 이 대화에 답해줘.

최신 구현 승인에서 1800자 상한을 명시해 이전800자 상한을 대체했다. 최종 본문은 1800 UTF-16 units/4096 UTF-8 bytes로 제한한다. 검증 결과·남은 live 준비는 실행 계획과 [사용 안내](../../discord-session-summaries.md)를 참조한다.
